# BitInstantView — iOS App

A Flutter application that gives the official **BitInstantView** cryptocurrency
trading website (<https://www.bitinstantview.com>) a secure, native iOS shell
built on `webview_flutter` (WKWebView). It is not a redesign of the website:
it is a focused, accessible native wrapper that adds the things a browser tab
cannot — a branded launch experience, reliable loading/offline/error states,
a centralized navigation-security policy, and quick access to the legal
pages and account-management entry points.

> **Read [`docs/APP_STORE_READINESS.md`](docs/APP_STORE_READINESS.md) and
> [`docs/TEST_REPORT.md`](docs/TEST_REPORT.md) before submitting to the App
> Store.** They document what has actually been verified, what is still
> blocked by this build environment, and what remains a business/legal
> dependency on the app owner.

## Technology stack

| Concern | Choice |
|---|---|
| App framework | Flutter (Dart) |
| iOS rendering | WKWebView via [`webview_flutter`](https://pub.dev/packages/webview_flutter) + [`webview_flutter_wkwebview`](https://pub.dev/packages/webview_flutter_wkwebview) |
| Connectivity signal | [`connectivity_plus`](https://pub.dev/packages/connectivity_plus) (supplementary only — see [Known limitations](#known-limitations)) |
| External link handling | [`url_launcher`](https://pub.dev/packages/url_launcher) |
| State management | Plain `ChangeNotifier` + `ListenableBuilder` (no Provider/Bloc/Riverpod — the app's single-screen, single-owner state does not need one) |
| Icons | `cupertino_icons` |

No analytics SDK, ad SDK, crash reporter, or third-party trading/market-data
API has been added. The only network traffic the app itself initiates is to
`bitinstantview.com` and the handful of external destinations the user
explicitly navigates to.

## Prerequisites

- Flutter **3.47.x** stable (Dart **3.13.x**) or a mutually compatible newer
  stable release. This repository was built and verified against Flutter
  3.47.7 / Dart 3.13.5.
- **macOS with Xcode** (current stable Xcode, with an iOS Simulator runtime
  installed) to build, sign, or run the iOS target. iOS apps cannot be built
  on Linux or Windows hosts — Apple's toolchain only runs on macOS. This
  repository was authored on a Linux cloud VM, which is why static analysis
  and the Dart test suite were run and verified here, while the actual
  `flutter build ios` step could not be — see
  [`docs/TEST_REPORT.md`](docs/TEST_REPORT.md) for the exact, reproducible
  evidence of that limitation.
- CocoaPods **or** Swift Package Manager. The iOS project generated by this
  Flutter version defaults to Swift Package Manager (no `Podfile` is
  committed); every plugin this app depends on (`webview_flutter_wkwebview`,
  `url_launcher_ios`) ships both an SPM `Package.swift` and a CocoaPods
  `.podspec`, so either toolchain works.

## Getting a build to test, without owning a Mac

This repository's own authoring environment is Linux with no Xcode, so no
`.ipa` or signed app can be produced here — that is an Apple platform
restriction, not a missing feature. **`.github/workflows/ios-build.yml`**
runs on every push to `main` using GitHub's hosted macOS runners (where
Xcode *is* available) and does the following, for real:

1. `flutter analyze`, `dart format --set-exit-if-changed`, `flutter test`
2. `flutter build ios --debug --simulator` — a genuine, working build for
   the **iOS Simulator**, zipped and uploaded as a workflow artifact
3. `flutter build ios --release --no-codesign` — a device-architecture
   build with no signing, as a release-pipeline sanity check (not
   uploaded, since an unsigned `.app` cannot be installed anywhere)

### To test the Simulator build

1. Open the [latest successful run](../../actions/workflows/ios-build.yml)
   of this workflow and download the `BitInstantView-ios-simulator`
   artifact (requires being signed in to GitHub).
2. On a Mac, unzip it and run:
   ```bash
   open -a Simulator
   xcrun simctl install booted Runner.app
   xcrun simctl launch booted com.bitinstantview.app
   ```

### To test on a real, physical iPhone/iPad

Apple requires every app installed on physical hardware to be
cryptographically signed with an Apple Developer certificate — there is no
way around this, by GitHub Actions, by this repository, or by any tool.
You have two real options:

- **Fastest (free, no CI changes needed):** on a Mac with Xcode installed,
  open `ios/Runner.xcworkspace`, sign in with your own Apple ID under
  *Signing & Capabilities* (free "Personal Team" signing works for
  installs that self-expire after 7 days), connect your iPhone/iPad over
  USB or Wi-Fi, select it as the run destination, and press **Run**. No
  App Store Connect account or paid membership is required for this.
- **Distributable build (ad hoc or TestFlight):** requires a paid Apple
  Developer Program membership, a real registered bundle identifier (see
  [Bundle identifier](#bundle-identifier) below), a distribution
  certificate + provisioning profile (or App Store Connect API key +
  Fastlane `match`), and the target devices' UDIDs registered for ad hoc.
  None of this exists in this repository because it requires credentials
  only the app owner's Apple Developer account can provide. Once you have
  them, add them as GitHub Actions secrets and extend
  `.github/workflows/ios-build.yml` with a signed `flutter build ipa`
  step — ask and this can be wired up.

## WebView navigation policy

All navigation-security decisions live in `lib/core/navigation/url_policy.dart`
and are unit-tested in `test/core/navigation/url_policy_test.dart`. In short:

- **First-party** (`bitinstantview.com` and real subdomains, HTTPS only) →
  loads inside the app's WebView.
- **The confirmed Google OAuth hop** (`accounts.google.com`, used by the
  live site's "Continue with Google" button) → also loads inside the
  WebView, so the sign-in redirect keeps the same session/cookie context
  instead of bouncing to an unrelated Safari session.
- **Any other HTTPS destination** → handed to the system browser
  (`url_launcher`, `LaunchMode.externalApplication`).
- **`mailto:` / `tel:` / `sms:` / `facetime:`** → handed to the matching
  native OS handler.
- **`javascript:`, `file:`, `data:`, `blob:`, `about:`, unrecognized custom
  schemes, and plain HTTP (including to the first-party host)** → blocked.
- Host matching uses Dart's `Uri` parser and checks real subdomain
  boundaries (`host == allowed || host.endsWith('.$allowed')`), never a
  substring match — so `bitinstantview.com.evil.org` or
  `evilbitinstantview.com` are **not** treated as first-party.

See `docs/APP_STORE_READINESS.md` for the live-site inspection that produced
this policy (confirmed routes, the Google OAuth link, the cookie-consent
banner, etc.).

## Testing

```bash
flutter test
```

70 unit and widget tests cover the URL policy, the error-mapping logic, the
WebView state machine's retry transitions, and the native UI (loading,
error/offline states, the accessible retry button, the settings screen).
See [`docs/TEST_REPORT.md`](docs/TEST_REPORT.md) for the full breakdown,
including what a `flutter test` run can and cannot exercise (there is no
real `WebViewPlatform` registered in the plain Dart test environment, so the
suite also verifies that the app degrades to an accessible error screen
instead of crashing when the WebView engine itself is unavailable — a real
defensive code path, not a mocked one).

Integration/simulator-level testing (actual page loads, gestures, keyboard
behavior, rotation) requires a macOS host with Xcode and is listed as
**blocked by environment** in the test report, not as passed or failed.

## Known limitations

- **No pull-to-refresh.** `webview_flutter`'s `WebViewWidget` is a platform
  view, not a `Scrollable`, so there is no reliable way to drive a Material
  `RefreshIndicator` from the WebView's own scroll position without a
  custom gesture hack that risks breaking the site's own scrolling, forms,
  and (if ever added) charts. Per the brief's own guidance, this feature is
  intentionally omitted rather than implemented unreliably. Users can pull
  down inside the page itself if BitInstantView's own site supports that, or
  use the native in-app Retry action.
- **`NetworkStatusService` is supplementary only.** It is never the sole
  reason a page load is treated as failed — the authoritative signal is
  always the WebView's own navigation delegate — because a device can
  report "connected" on an interface with no real route to the internet,
  and vice versa.
- **No `package_info_plus` dependency.** It was tried for the Settings
  "Version" row, but its platform-channel call hung indefinitely under
  `flutter test`'s `TestWidgetsFlutterBinding` in this Linux build
  environment (even past an explicit `Future.timeout`), which is not an
  acceptable risk for a single, low-value display string. The version is
  now a plain constant (`AppConfig.appVersion` / `appBuildNumber`) that must
  be kept in sync with `pubspec.yaml`'s `version:` field by hand on each
  release.
- **No native Sign in with Apple.** The live site offers "Continue with
  Google" as a third-party login option, which can trigger Apple's
  Guideline 4.8 requirement for an equivalent privacy-preserving sign-in
  option. The app does not implement any login UI itself (sign-in happens
  entirely inside the website's own WebView flow), and adding Sign in with
  Apple would require the BitInstantView backend to support it, which is
  outside this repository's control. See `docs/APP_STORE_READINESS.md`.
- **iOS build/signing/simulator testing is blocked in this authoring
  environment** (Linux, no Xcode). Everything that can be verified without
  Xcode — static analysis, formatting, the full Dart test suite, and manual
  inspection of the generated Xcode project files/asset catalog — has been
  verified and is documented in `docs/TEST_REPORT.md`.
